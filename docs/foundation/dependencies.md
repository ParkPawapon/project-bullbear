## Locks and integrity

- Gradle generated strict dependency locks for the compile and runtime classpaths of both main and test sources. The module sets are shared across hosts because the backend resolves the same declared platform classifiers. The Java test dependencies stay off the desktop runtime classpath.
- The Wrapper ZIP and Wrapper JAR were checked against the published SHA-256 values. The build verifies the dependency metadata and artifacts in [verification-metadata.xml](../../gradle/verification-metadata.xml).
- The initial 162 artifact entries were compared with repository checksum sidecars over HTTPS. During GitHub hardening, 13 added or changed artifact checksums matched Maven Central, leaving 172 SHA-256 pins in total. Gradle verifies those pins during resolution. The OSV advisory lookup on 2026-11-26 reported no matches for the 74 Maven coordinates in the updated manifest. Publisher-signature verification is outside this check.
- Gradle's `settings-gradle.lockfile` records an empty dependency set for the version catalog input. It was generated by the same lock-writing command.

When changing a pin, run the command below with the JDK 21 toolchain. Review the newly resolved versions, classifiers, and changed checksums against the approved source. Then run `clean check` and build the distribution again in strict mode.

```sh
./gradlew spotlessCheck build :desktop:installDist --write-locks --write-verification-metadata sha256
```

On Windows use `.\gradlew.bat` in place of `./gradlew`. For a Wrapper upgrade, generate the Wrapper and compare its JAR checksum with Gradle's published value. CI pins actions to their release commits. Confirm each new tag-to-commit mapping before changing a pin.
